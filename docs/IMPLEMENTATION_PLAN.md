Перелік функціоналу з ідентифікаторами (RUL-*, OOX-*, RTY-*, GUI-* тощо) — у [FEATURES.md](FEATURES.md).

## 1. Архітектура

```
 ┌──────────── SPOReplaceLink.exe (десктопний застосунок, сесія користувача) ────────────┐
 │  Вікно WPF + WebView2: дашборд, прогони, файли, помилки, налаштування (Blazor, MudBlazor)│
 │  Engine: оркестрація прогонів, черги, повтори, пауза/продовження                        │
 │    ├─ Spo: MSAL, Graph, перелік, завантаження/вивантаження                              │
 │    ├─ OpenXml: заміни в xlsx/xlsm/xlsb, пошук залишків                                  │
 │    └─ ExcelWorker-пул ──► окремі процеси EXCEL.EXE (xls, залишки xlsb)                  │
 │  State: SQLite (прогони, файли, спроби, заміни)                                         │
 │  Локальний REST API (localhost) ◄── CLI (розклад, автоматизація)                         │
 └─────────────────────────────────────────────────────────────────────────────────────────┘
```

Ключові рішення:
- **Один десктопний застосунок, з якого керується все.** Рушій, стан і інтерфейс — в одному процесі; інтерфейс — ті самі сторінки Blazor у вікні WebView2 (бібліотека `SPOReplaceLink.Ui`). Спершу планувався вебінтерфейс у браузері; за рішенням замовника — десктоп.
- **Рушій не залежить від вікна.** Закриття вікна під час прогону питає: згорнути в трей (прогін триває) чи плавно зупинити. Будь-який перерваний прогін продовжується після наступного запуску з того самого місця (STA-3), тож прив'язка до сесії не загрожує даним.
- **Застосунок працює в сесії користувача.** Тому Excel COM для xls (етап 4) працює без обхідних рішень. Ціна — прогін іде, поки користувач у системі; для довгих прогонів на ВМ — автовхід і запуск застосунку при вході.
- **Налаштування — в GUI.** Підключення, профілі прогону і шаблони заміни зберігаються в базі застосунку. JSON-експорт та імпорт — для CLI і перенесення між середовищами. Кожен прогін зберігає знімок налаштувань, тож результат завжди можна пояснити.
- **CLI — тонкий клієнт** до локального API відкритого застосунку (запуск прогону з профілю, статус, експорт), плюс автономна команда `local`. Ядро без вікна (`spo-replace-link-host`) лишається для тестів і автоматизації.
## 2. Технічний стек

| Компонент | Вибір | Причина |
|---|---|---|
| Платформа | .NET 10 (LTS, до листопада 2028) | Один стек для рушія, UI і CLI; спершу був .NET 8, перейшли через виправлення ZipArchive у режимі Update (порожні стиснуті частини) і кінець підтримки .NET 8 у листопаді 2026 |

| Оновлення в реальному часі | Таймер у компоненті дашборду (раз на 2 с) | Сторінки працюють у тому ж процесі, що й рушій |
| CLI | System.CommandLine | Команди і параметри з довідкою |

| Тести | xUnit + bUnit (компоненти UI) + тестові файли | Регресія на реальних прикладах |

## 4. Конвеєр обробки одного файлу

```
pending
  └─ download (Graph, eTag, versionId)             → downloaded
       └─ route за форматом
            ├─ xlsx/xlsm → OpenXml
            ├─ xlsb      → OpenXml (.rels) → є залишки в .bin? → черга ExcelWorker
            └─ xls       → черга ExcelWorker
       └─ пошук залишків (RES-1)                   → processed
       └─ змін немає?  → unchanged
       └─ режим scan?  → planned
       └─ upload з If-Match                         → done
            ├─ 412 → conflict → рівень 2 повторів
            └─ 423 / check-out → locked → відкладені (рівень 3)
  будь-яка помилка → класифікація (RTY-1) → запис спроби (RTY-2)
       ├─ клас з автоповтором і спроби не вичерпано → назад у чергу з паузою
       └─ інакше → failed:<клас> (потребує уваги)
```

Паралельність: окремі обмежені черги для завантажень з мережі, обробки на CPU, вивантажень і ExcelWorker. Мережеві черги автоматично стискаються під час throttling (RSL-2).

## 5. Повторна обробка (як реалізовано)

Повний опис вимог — FEATURES.md, розділ 9. Технічно:

- **Таблиця `attempts`** у базі стану: кожна спроба по кожному файлу (час, етап, клас, HTTP-код, `request-id`, повідомлення). Статус файлу в таблиці `files` — похідний від останньої спроби.
- **Черга з затримкою** в Engine: файл, що повертається на повтор, отримує `not_before`; планувальник бере файли, у яких цей час настав. Паузи і ліміти — з конфігу прогону.
- **Відкладені файли** (`locked`) мають окрему чергу, яку планувальник обходить хвилями після основної, до ліміту часу.
- **Повторний прогін** — новий запис у таблиці `runs` з посиланням на батьківський прогін і списком файлів, відібраних фільтром. Бібліотека повторно не перелічується; кожен файл завантажується заново зі свіжим eTag.
- **Гарантія завершення:** прогін переходить у `completed` / `completed_with_errors` лише коли в ньому немає файлів у проміжних статусах.
- **Відновлення після падіння хоста:** на старті файли в проміжних статусах (`downloaded`, `processed`) повертаються в `pending`. Повторна обробка безпечна завдяки ідемпотентності і `If-Match`.

## 6. Дашборд і налаштування (як реалізовано)

- **Метрики:** швидкість, RU і throttling рахуються в Engine в пам'яті; лічильники статусів дашборд бере з бази індексованими запитами (кеш 1 с) — так вони точні й після перезапуску, і вкладаються в 1 с на 200 тис. файлів. Важкі розбивки й графіки завантажуються у фоні, не затримуючи показ сторінки.
- **Таблиці файлів і помилок** читаються з SQLite посторінково з індексами за статусом, класом, бібліотекою, форматом.
- **Часові ряди** (прогрес, швидкість, помилки) — знімок метрик раз на хвилину в таблицю `run_metrics`, щоб графіки будувалися і для завершених прогонів.
- **Команди з UI** (старт, пауза, повтор, ігнорувати) викликають ті самі методи Engine, що й REST API для CLI.
- **Налаштування** зберігаються в таблицях `connections`, `profiles`, `templates`, `rules`, `config_history`. Одна модель налаштувань (C#-класи з валідацією) використовується і формами GUI, і JSON-імпортом, і CLI — тому правила валідації однакові всюди.
- **Знімок налаштувань:** на старті прогону профіль разом із шаблонами серіалізується в JSON і зберігається в `runs.config_snapshot`. Engine працює лише зі знімком.
- **Вибір цілей:** сайт за URL (`sites/{hostname}:/{path}`) або пошуком (`sites?search=`), бібліотеки (`sites/{id}/drives`), папки (`drives/{id}/items/{id}/children`). З правами `Sites.Selected` пошук сайтів може повертати порожній результат, тому введення URL — основний спосіб, пошук — допоміжний.
- **Зміна паралельності на льоту** (GUI-21): ліміти черг — змінні семафори в Engine, що оновлюються командою з UI.

## 7. Керування навантаженням на SPO (як реалізовано)

Вимоги — FEATURES.md, розділ 11.1 (THR-*).

**Скільки дає один застосунок.** Орієнтовна пропускна здатність при роботі на 80% ліміту застосунку і ~4 RU на змінений файл (THR-4), без урахування внутрішніх лімітів SPO; уточнюється на пілоті:

| Ліцензій у тенанті | Ліміт застосунку | Змінених файлів / год | Змінених файлів / добу (добовий ліміт) |
|---|---|---|---|
| до 1 000 | 1 250 RU/хв | ~15 тис. | ~240 тис. |
| 1 001 – 5 000 | 2 500 RU/хв | ~30 тис. | ~480 тис. |
| 5 001 – 15 000 | 3 750 RU/хв | ~45 тис. | ~720 тис. |

Файли без змін коштують ~2 RU, тобто обробляються вдвічі швидше. Отже, бібліотека на 100 тис. файлів укладається в кілька годин одним застосунком. На практиці раніше обмежать затримки мережі і пікові години, а цього кілька застосунків не вирішують.

**Механізм:**
- **Облік RU.** Кожен вихідний запит проходить через `RuBudget` застосунку: вартість запиту береться з таблиці Microsoft (1/2/5 RU), запит чекає, поки в token bucket (хвилинне вікно) і в ковзному добовому лічильнику є місце. Ліміти — з діапазону ліцензій (THR-2), поріг — з профілю.
- **Стан throttling на рівні застосунку.** 429/503 з `Retry-After` переводить застосунок у стан «пауза до T»; усі потоки цього застосунку чекають. Після паузи паралельність відновлюється поступово (адитивне збільшення, мультиплікативне зменшення при новому 429).
- **Розклад.** Планувальник перевіряє вікна роботи профілю (THR-5) і перемикає бюджет або ставить прогін на паузу; продовження — автоматичне.
- **Блокування.** Якщо протягом N хвилин усі запити застосунку отримують 503, прогін зупиняється зі статусом «можливе блокування SPO» (THR-7).
- **Пул застосунків (етап 2).** `AppPool` тримає кілька підключень, кожне зі своїм MSAL-клієнтом, `RuBudget` і станом throttling. Над ними — `TenantBudget`, що обмежує суму споживання часткою тенантного ліміту (THR-10). Файл закріплюється за застосунком на весь цикл обробки; при паузі одного застосунку нові файли отримують інші. Перелік файлів (delta) виконує один застосунок пулу, щоб delta-токен був послідовним.

Оцінки — орієнтовні, для одного розробника; уточнюються після етапу 1.

### Етап 0. Підготовка (1–2 дні, паралельно з етапом 1)

### Етап 1. Рушій правил і обробка OOXML (5–7 днів)

Функціонал: CFG-1, CFG-4, CFG-7, RUL-1…RUL-6, RUL-8, RUL-9, OOX-1…OOX-4, OOX-10…OOX-12, OOX-14, OOX-15, XLB-1, XLB-2, RES-1, RES-2, REP-1, REP-2, команда `local`.

1. Каркас рішення, збірка, базові тести.
2. Нормалізація URL: регістр, percent-encoding (включно з кирилицею), слеші, межі сегментів.
3. Рушій правил: один прохід, найдовший збіг, валідація набору, `rules test`.
4. Розв'язання відносних посилань відносно старого розташування документа.
5. Обробка zip: переписування лише змінених частин, решта байт-у-байт.
6. Обробники частин: `.rels` (Hyperlinks, externalLinks), `externalLinkN.xml` (`absoluteUrl`), формули `<f>`.
7. Пошук залишків у всіх частинах (UTF-8 і UTF-16LE), маркування xlsb для ExcelWorker.
8. Самоперевірка результату, виявлення зашифрованих файлів.
9. Команда `local`: обробка папки, звіти CSV.

**Критерій готовності:** усі тестові xlsx/xlsm після `local` відкриваються в Excel без попереджень про відновлення; Edit Links і гіперпосилання вказують на нові адреси; повторний прогін дає 0 змін.

**Стан (23.10.2026): реалізовано.** 117 автотестів. На файлах, створених Excel (`tests/excel`), критерій виконано: xlsx/xlsm відкриваються без відновлення, Edit Links і гіперпосилання нові, зовнішній зв'язок читає дані з нового джерела, повторний прогін — 0 змін. У xlsb виправлено `.rels`; формула HYPERLINK у бінарному аркуші лишається до етапу 4 (файл отримує `needs_excel`). Швидкодія локально: 1 000 файлів за ~2 с, аркуш 33 МБ XML з 200 тис. замін — ~8 с. Реальні файли замовника (етап 0) ще не перевірені.

Що з'ясувалося на файлах Excel і враховано:
- Excel пише URL з пробілами як `%20`, а кирилицю — як є. Хвіст посилання копіюється без змін, новий префікс записується в тому ж стилі.
- Зовнішню книгу Excel зберігає трьома посиланнями: основне (часто шлях без диска, `/Users/…`), `absoluteUrl` (`file:///C:\…`) і `relativeUrl` (`../…`). Виправляються всі три; шлях без диска розв'язується від кореня розташування документа.
- `x15ac:absPath` у `workbook.xml` (де файл зберігали востаннє) оновлюється разом з іншими змінами, але сам по собі не є приводом записувати файл і не вважається залишком. У xlsb відповідний запис (BrtAbsPath15) виключається з пошуку залишків.
- Режим оновлення `ZipArchive` у .NET зберігає стиснені байти незмінених частин; це перевіряється при кожному записі (CRC, розміри). Архів при цьому тримається в пам'яті — для файлів у сотні МБ варто стежити за пам'яттю на етапі 2.

### Етап 2. SharePoint, Engine, стан, повтори, навантаження, пул застосунків (10–14 днів)

Функціонал: CFG-2, CFG-3, CFG-5, CFG-6, ENU-1, ENU-3, UPL-1…UPL-4, UPL-6, STA-1…STA-5, RTY-1…RTY-8, RSL-1…RSL-6, THR-1…THR-7, THR-9…THR-11, REP-3, REP-4, SEC-1…SEC-3.

1. MSAL (сертифікат; резервний варіант device code), обробка 401.
2. Graph-клієнт: політики повторів, Retry-After, User-Agent, адаптивна паралельність.
   Облік RU (`RuBudget`), стан throttling на рівні застосунку, добовий бюджет, вікна роботи, виявлення блокування.
   Пул застосунків: `AppPool` (окремий MSAL-клієнт, `RuBudget` і стан throttling на кожен застосунок), `TenantBudget` зі стелею тенантного бюджету, закріплення файлу за застосунком, перерозподіл нових файлів при паузі застосунку, перевірка доступу кожного застосунку до всіх цілей перед стартом.
3. Перелік через delta зі збереженням позиції.

**Стан (23.10.2026): реалізовано, перевірено на емуляторі Graph; на реальному тенанті не перевірялось** (немає зареєстрованого застосунку, відкрите питання 1).

Що зроблено:
- **Проєкти:** `Spo` (MSAL, Graph-клієнт, облік RU, стан throttling, пул), `State` (SQLite), `Engine` (рушій прогону, `RunService`, звіти), `Host` (REST API, Serilog JSON lines, автопродовження перерваного прогону), CLI-клієнт.
- **Тести:** емулятор Graph (`tests/Shared/FakeGraph.cs`) відтворює delta зі сторінками, eTag та `If-Match`, версії, check-out, 423, upload session, а також збої 401/403/412/423/429/503 і обрив з'єднання.
- **Критерії, перевірені на емуляторі:**
  - `apply` → `verify` дає 0 залишків, повторний `apply` — 0 вивантажень;
  - «вбивство» хоста одразу після вивантаження: після перезапуску жоден файл не вивантажено вдруге;
  - 401/412/423/429/503 оброблено за таблицею 9.1, і кожен файл отримує фінальний статус;
  - пул із двох застосунків: throttling одного не зупиняє обробку, сумарне споживання не перевищує стелі тенанта.
- **Незалежне рев'ю коду** знайшло 9 проблем, виправлено всі, на кожну є регресійний тест (`ReviewRegressionTests`):
  - блокування одного застосунку зупиняло весь пул;
  - неоднозначне вивантаження (відповідь загубилась, хост упав під час запису) позначалося як «видалено» або «без змін». Тепер перед записом фіксується намір: версія, eTag і SHA-256 вмісту. Після збою вміст звіряється з тим, що лежить у SharePoint;
  - збій переліку не через помилку Graph міг підвісити прогін;
  - дочірні прогони брали застарілий eTag;
  - хвилі відкладених файлів витрачали спроби повторів;
  - помилка запису стану всередині воркера лишала файл в обробці назавжди;
  - вичерпаний добовий бюджет RU перетворювався на помилки файлів, тепер це пауза;
  - під час вивантаження частинами If-Match перевірявся лише на старті, тепер eTag звіряється і перед останньою частиною.
- **Відхилення від плану:** повтори реалізовано власним циклом у `GraphClient` замість Polly. Пауза за `Retry-After` має діяти на весь застосунок, а не на окремий запит, а Polly цього не дає без обхідних рішень.

Ще не перевірено, потребує пілоту:
- реальні MSAL і Graph;
- фактична вартість RU на файл;
- поведінка SPO під навантаженням;
- чи віддає SPO у `$select` поля `publication` і `listItem/fields` (версія і check-out);
- чи не переписує SPO файл під час збереження (оновлення властивостей документа з колонок бібліотеки). Якщо переписує, звірка за SHA-256 після втраченої відповіді не впізнає наш запис. Подвійного запису все одно не буде, але файл отримає статус `unchanged` замість `done`.

**Критерій готовності:** на пілотній бібліотеці `apply` → `verify` дає 0 залишків для xlsx/xlsm; примусове завершення хоста посеред прогону і перезапуск доводять роботу до кінця без дублювання; штучно спричинені 401/412/423/429/503 обробляються за таблицею 9.1, жоден файл не лишається без фінального статусу; на пілоті з порогом 80% бюджету RU немає 429 (або вони поодинокі і застосунок коректно стає на паузу); заміряна фактична вартість RU на файл; з пулом із 2+ застосунків сумарне споживання не перевищує стелі тенантного бюджету, а штучний throttling одного застосунку не зупиняє обробку іншими.

### Етап 4. ExcelWorker: xls і залишки xlsb (4–6 днів)

Функціонал: XLS-1…XLS-5.

1. Окремий процес-обробник і протокол обміну з хостом (вхідний файл → вихідний файл + JSON-результат).
2. Відкриття без оновлення зв'язків і макросів, без діалогів; `ChangeLink`, `Hyperlinks`, формули.
3. Пул процесів Excel, таймаути, примусове завершення зависань, перезапуск.
4. Інтеграція в Engine (клас помилки `excel`) і в дашборд (стан пулу).

**Критерій готовності:** усі тестові xls і xlsb з `HYPERLINK()` виправлені; штучне зависання Excel не зупиняє прогін; після прогону не лишається процесів `EXCEL.EXE`.

**Стан (26.10.2026): реалізовано, критерій перевірено на Excel 365 (українська локалізація).** 267 автотестів, з них 40 нові для етапу 4; 7 перевіряють справжній Excel і виконуються лише там, де він встановлений (без Excel вони проходять без перевірок).

Як зроблено:
- **Обробник.** `SPOReplaceLink.ExcelWorker.exe` тримає один прихований Excel. Обмін з хостом — JSON-рядками через stdin/stdout, операції `convert` (відкрити й зберегти в іншому форматі) та `inspect` (які посилання бачить Excel).
  - Файл відкривається лише для читання, без оновлення зв'язків, з вимкненими макросами й без діалогів.
  - Пароль на відкриття: передається пароль, що свідомо не підходить. Excel відмовляє одразу, а не чекає на введення, і файл отримує `skipped:encrypted`.
  - Файл, який Excel відкрив не як книгу (текст із розширенням xls), відхиляється (`failed:file`).
  - Зайняті COM-виклики повторюються через message filter.
- **Заміна.** Без `ChangeLink`: Excel зберігає копію як xlsm, посилання в ній замінює той самий рушій, що й для xlsx (правила, місця заміни, самоперевірка), і Excel зберігає результат назад в оригінальному форматі. Записаний файл відкривається в Excel ще раз: усе, що Excel показує в Edit Links, гіперпосиланнях і формулах і що правила ще змінили б, стає залишком.
- **Пул.** N процесів Excel з профілю (GUI-20, за замовчуванням 2) і таймаут на операцію (за замовчуванням 5 хв).
  - Зависання: обробник і його Excel завершуються за ідентифікатором процесу, файл отримує ще одну спробу в новому процесі (клас `excel`, FEATURES 9.1).
  - Процеси перезапускаються кожні 200 операцій.
  - Пул живе стільки, скільки прогін. Запущені процеси записуються у файл, який пул тримає відкритим; після аварійного завершення хоста наступний запуск завершує те, що лишилося. Процес завершується, лише якщо збігаються ідентифікатор і час старту, тож чужий Excel не зачіпається.
- **Рушій.** Етап `excel` після обробки OOXML. Без Excel файли отримують `needs_excel` з причиною. Дашборд показує стан пулу: зайнято / запущено, операції, зависання, падіння. `local` у CLI теж обробляє xls (`--excel N`).

Перевірено:
- Тестові файли з `tests/excel` (`New-ExcelFixtures.ps1` тепер створює і xls):
  - xls і xlsb після `local` проходять `Test-ExcelOutput.ps1` — Edit Links, гіперпосилання, `HYPERLINK()`, зв'язок читає нове джерело;
  - формат зберігається (xls — 56, xlsb — 50);
  - кешоване значення зовнішнього посилання не змінюється;
  - повторний прогін дає 0 змін.
- Автотести на справжньому Excel:
  - xls і xlsb з посиланнями в усіх місцях виправлені, повторна обробка дає 0 змін;
  - кешовані значення зберігаються;
  - зависання Excel (обробник перестає відповідати) — і обробник, і `EXCEL.EXE` завершено;
  - після закриття пулу `EXCEL.EXE` не лишається.
- Автотести рушія з обробниками в тестовому режимі (без Excel):
  - xls проходить apply → verify;
  - файл, на якому Excel «зависає», отримує дві спроби і `failed:excel`, решта прогону завершується;
  - без Excel — `needs_excel`.
- Демо (`DemoSeed`): справжній xls проходить scan → apply → verify; після прогонів процесів Excel не лишається.

Відхилення від плану:
- `ChangeLink` не використовується (див. вище). Перевірка на Excel показала: якщо нове джерело недоступне з машини, де працює Excel (типово для адрес SharePoint), `ChangeLink` замінює кешовані значення на `#REF!`.
- **Побічна дія збереження.** Excel, зберігаючи копію в тимчасовій папці, переписує посилання на файли того ж диска відносно цієї папки. Тому копія лежить на 8 рівнів глибше за корінь (`LocalCopy`). Посилання, що вказує всередину кореня, було відносним до документа; посилання поза коренем було абсолютним локальним шляхом.
- Обробник — `net10.0` з пізнім зв'язуванням COM, а не `net10.0-windows`, щоб на нього могли посилатися хост і CLI.

Обмеження: посилання на файл на тому самому локальному диску, що й тимчасова папка (за замовчуванням C:), Excel зберігає без літери диска. Відкрите з SharePoint, таке посилання вказувало б не туди. Тому файл з таким посиланням не записується і отримує `failed:validation` з поясненням. Обробити його можна з папкою даних застосунку на іншому диску (`--data`) або з `local --temp`. Посилання на SharePoint, мережеві шляхи і інші диски це не зачіпає. Тестові файли з `tests/excel` посилаються на C:, тому перевіряються з `--temp D:\…`.

Незалежне рев'ю коду етапу знайшло 7 проблем; виправлено всі, на кожну є тест або перевірка:
- посилання на диск тимчасової папки тихо втрачало літеру диска (див. обмеження вище);
- один збій запуску Excel вимикав Excel до кінця прогону — тепер це падіння з повтором, «недоступний» лише коли Excel чи обробника немає;
- Excel, що завис під час запуску, лишався працювати — тепер обробник повідомляє його ідентифікатор одразу після запуску;
- таймаут файлу під час роботи Excel класифікувався як мережевий; додано попередження, якщо таймаут файлу менший за три таймаути Excel;
- незрозуміла відповідь обробника не вважалася падінням, і він міг віддати відповідь для іншого файлу;
- робоча папка попередньої спроби, яку не вдалося видалити, давала остаточний `failed:file`;
- помилки пароля чи пошкодженого файлу на другій операції Excel вважалися збоєм Excel; повтор Excel могли «з'їсти» інші помилки; `local` без Excel давав `failed:excel` замість `needs_excel`.

Ще не перевірено:
- реальні xls замовника (етап 0);
- xls з макросами (проміжний формат xlsm макроси зберігає, але на справжніх файлах це не перевірялось);
- поведінка під тривалим навантаженням (сотні xls поспіль).

### Етап 5. Пілот і доопрацювання (3–5 днів)

1. `inventory` на реальних бібліотеках → доповнення правил.
2. `scan` → вибіркова ручна перевірка звіту замін.
3. `apply` на одній реальній бібліотеці → `verify` → перевірка користувачами ключових файлів.
4. Виправлення знайдених проблем, оновлення тестових файлів.
5. Інструкція для адміністратора: розгортання хоста, запуск прогону, робота з помилками.

**Стан (26.10.2026): MVP завершено в частині, яку можна зробити без тенанта; сам пілот (кроки 1–4) чекає на зареєстрований застосунок і пілотну бібліотеку (відкриті питання 1, 5, 6).** 275 автотестів, з них 8 нові для етапу 5.

Що зроблено:
- **Звіт пілоту** (`pilot`; у GUI — «Звіти → Звіт пілоту», у CLI — `export`). Містить:
  - файли за форматами;
  - витрачені RU, 429/503 і **RU на файл** порівняно з планом THR-4. Лічильники підсумовуються за всі запуски прогону (знімок метрик тепер містить час старту сесії, бо після перезапуску метрики рахуються з нуля);
  - швидкість за час активної обробки (хвилини, коли файли завершувалися: без очікування вікон, пауз і перерв між запусками), секунди на файл, межу швидкості за бюджетом RU (найбільший бюджет профілю з урахуванням вікон, хвилинного і добового ліміту, стелі пулу) і прогноз на 10 000 файлів та на профіль;
  - відповіді на два питання етапу 2, які можна з'ясувати лише на реальному SharePoint:
    - чи віддає SharePoint номер версії в `$select` — частка записаних файлів з `version_before`;
    - чи змінює SharePoint файл під час збереження — рушій тепер порівнює розмір, який повернув SharePoint, з розміром вивантаженого файлу (метрика `resizedBySpo`);
  - Excel: операції, зависання, падіння;
  - спроби з конфліктом і блокуванням, включно з тими, після яких файл записався (один агрегований запит);
  - помилки, згруповані з рекомендаціями;
  - перелік ручних перевірок.

  Звіт і вибірка читають файли одним проходом, без утримання всіх рядків у пам'яті, тож працюють і на прогонах у сотні тисяч файлів.
- **Вибірка для ручної перевірки** (`sample`): 30 змінених файлів у фіксованому псевдовипадковому порядку (той самий прогін — та сама вибірка), з адресою файлу, номером версії до запису, прикладами замін і порожніми стовпцями `checked` / `comment` для перевіряльника.
- **Інструкція користувача** [USER_GUIDE.md](USER_GUIDE.md):

  - довідник усіх полів кожного екрана (що це, навіщо, ефект, значення за замовчуванням);
  - статуси, класи помилок з діями, звіти, CLI, діагностика.
- **Довідка в застосунку:**
  - `USER_GUIDE.md` вбудовано в збірку `SPOReplaceLink.Ui` і розбито на сторінки за заголовками: частини групують розділи, розділ із підрозділами (наприклад, вкладки профілю) має окрему сторінку на кожен підрозділ;
  - сторінка «Довідка»: дерево розділів, пошук за словами, кнопки «попередній / наступний»;
  - посилання всередині інструкції відкривають відповідний розділ: ідентифікатори — це якорі заголовків, як на GitHub;
  - кнопки «?» біля заголовків екранів, на кожній вкладці профілю, у діалогах запуску й повтору відкривають потрібний розділ у вікні;
  - тести перевіряють, що кожне внутрішнє посилання інструкції і кожна кнопка «?» ведуть на існуючий розділ: перейменування заголовка не зламає довідку непомітно;
  - самоперевірка `--selftest` відкриває довідку і вікно «?» і зберігає знімки поруч із результатом (`*.help.png`, `*.help-dialog.png`).
- **Дрібні виправлення, знайдені під час написання інструкції:**
  - у фільтрах файлів і повторів не було класу `excel` (`failed:excel`);
  - таблиця «Місця заміни» показувала для xls «етап 4» замість «через Excel»;
  - підказка CLI посилалася на неіснуючий `spo-replace-link-host`.

Незалежне рев'ю коду етапу і звірка інструкції з кодом. Виправлено:
- звіт пілоту: недорахунок блокувань (спроби з 423 перед успішним записом), запит до бази на кожен файл, швидкість з урахуванням простоїв, межа бюджету без вікон і добового ліміту, втрата лічильників між сесіями, утримання всіх файлів у пам'яті;
- прогін, перерваний до старту обробки, не записував знімок метрик (RU на підготовку цілей губилися);
- помилка побудови звіту в GUI ламала сторінку замість повідомлення;
- в інструкції 15 неточностей:
  - inventory розбирає кожен файл, як scan;
  - «Зупинити» перериває поточні файли, крім тих, що вже записуються;
  - фактичні кількості повторів і робота запобіжника;
  - пауза не переживає перезапуск;
  - звичайний вихід лишає прогін «зупиненим»;
  - поведінка при зайнятому порті;
  - маска шляху в повторі та інші дрібниці.

Відомі обмеження, виявлені рев'ю (не виправлялись):
- **Перезавантаження Windows.** Застосунок не обробляє завершення сеансу: під час прогону вікно показує запитання, і Windows може його закрити примусово. Тоді прогін продовжиться сам як перерваний.
- **Зміна файлу в SharePoint.** Перевіряється лише за розміром у відповіді на запис. Якщо SharePoint змінює файл пізніше, звіт цього не покаже.
- **Пауза** не зберігається після перезапуску застосунку.

Ще не зроблено (потребує тенанта):
- пілот: `inventory` → правила → `scan` → `apply` → `verify` → перевірка користувачами на реальній бібліотеці;
- реальні файли замовника (етап 0);
- заміри RU і швидкості. Звіт пілоту дає їх одразу після першого прогону `apply`.

## 10. Порядок бойового прогону

1. `inventory` по всіх цілях → узгодження правил.
2. `scan` → перегляд звіту в GUI, вибіркова перевірка.
3. `apply` по одній бібліотеці → `verify` → перевірка користувачами.
4. `apply` по решті бібліотеках партіями, у неробочий час.
5. Перегляд помилок у GUI → повторний прогін для виправних, «ігнорувати з коментарем» для решти.
6. Фінальний `verify`, експорт звітів, архівування бази стану.

Відкат — історія версій SPO (номер версії до запису зберігається в базі); після етапу 6 — команда `rollback`.

## 11. Ризики

| Ризик | Вплив | Як зменшити |
|---|---|---|
| Неповна таблиця відповідності шляхів | Частина посилань лишиться битою | `inventory` з гістограмою префіксів до початку замін |
| Користувачі редагують файли під час прогону | Конфлікти, заблоковані файли | `If-Match` + повтор; відкладені хвилі; неробочий час |
| Throttling SPO на великих обсягах | Падіння швидкості | Бюджет RU нижче ліміту, мінімум запитів на файл, пауза всього застосунку за `Retry-After`, User-Agent, вікна неробочого часу |
| Пул застосунків виснажує тенантний бюджет | Throttling користувачів та інших застосунків (бекап, міграція); блокування застосунку Microsoft | Пул вмикається в профілі явно, з попередженням; стеля тенантного бюджету (THR-10); виявлення блокування і зупинка (THR-7) |
| Паралельно працюють інші важкі застосунки (міграція, бекап) | Менше тенантного бюджету, ніж розраховано | Уточнити розклад інших інструментів; вікна роботи; моніторинг 429 на дашборді |
| Excel COM нестабільний | Зависання на xls | Окремі процеси, таймаути, примусове завершення; або Aspose.Cells |
| ВМ перезавантажилась / сесію користувача завершено | Прогін зупинився | Автовхід + автозапуск хоста; продовження з бази стану; сповіщення (GUI-15) |
| Нестандартні місця зберігання посилань | Пропущені посилання | Пошук залишків у всіх частинах файлу — видно у звіті |
| Кожне вивантаження створює нову версію і змінює Modified | Шум в історії | Лише змінені файли; UPL-5 на етапі 6 |
| Ліміт версій у бібліотеці | Видалення найстаріших версій | Перевірити налаштування версіонування до прогону |
