# SPOReplaceLink — перелік функціоналу

Інструмент для масової заміни битих посилань в Excel-файлах (xlsx, xlsm, xlsb, xls) у бібліотеках SharePoint Online після міграції.
Заміна ReplaceMagic.Excel з фокусом на **надійність, прогнозованість, швидкість**.

Пріоритети: **MVP** — потрібне для першого бойового прогону; **P2** — бажане, другий етап; **P3** — за потреби.

---

## 1. Ключові принципи

| # | Принцип | Що це означає на практиці |
|---|---|---|
| P-1 | Excel не працює з мережею | Файл завантажується через Graph, обробляється локально, завантажується назад. Жодних WebDAV, синхронізації чи сесій браузера. |
| P-2 | Без Excel, де це можливо | xlsx, xlsm і `.rels` у xlsb редагуються як zip з XML. Excel COM використовується лише для xls і залишків xlsb. |
| P-3 | Детермінованість | Однакові вхідні дані та правила завжди дають однаковий результат. Порядок правил не впливає на результат. |
| P-4 | Ідемпотентність | Повторний прогін по вже виправлених файлах не змінює нічого і нічого не завантажує. |
| P-5 | Нічого не пропускається мовчки | Кожен файл отримує фінальний статус. Кожне посилання, що лишилося зі старим префіксом, потрапляє у звіт. |
| P-6 | Відновлюваність | Після падіння або зупинки прогін продовжується з того самого місця. |
| P-7 | Безпечність за замовчуванням | Режим за замовчуванням — dry-run. Запис у SPO лише в режимі `apply`. |
| P-8 | Кожна невдача має наступний крок | Помилки класифікуються, тимчасові повторюються автоматично, решту можна повторити вибірково без повного проходу бібліотеки (розділ 9). |
| P-9 | Обробка не залежить від інтерфейсу | Рушій працює як окремий фоновий процес. Закриття браузера чи падіння GUI не зупиняє прогін (розділ 10). |

## 3. Правила заміни

| ID | Функція | Пріоритет |
|---|---|---|
| RUL-1 | Правило = старий префікс → новий префікс (за URL, а не довільний текст). | MVP |
| RUL-2 | Один прохід, найдовший збіг виграє. Замінений текст повторно не перевіряється. Порядок правил у файлі не має значення. | MVP |
| RUL-3 | Нормалізація перед порівнянням: регістр (SPO нечутливий до регістру), `%20` і інший percent-encoding (включно з кирилицею), `\` ↔ `/`, кінцевий слеш. | MVP |
| RUL-4 | Збіг лише на межі сегмента шляху: `/Document/` не збігається з `/Documents/` чи `/MyDocument/`. | MVP |
| RUL-5 | Збереження формату запису: якщо в оригіналі URL закодований, результат теж закодований тим самим способом. | MVP |
| RUL-6 | Відносні посилання (`../Analytics/a.xlsx`) розв'язуються відносно **старого** розташування документа, до них застосовуються правила, результат записується як абсолютний URL. Якщо правило не спрацювало, посилання не чіпається. | MVP |
| RUL-7 | Посилання з шляхом у query-рядку (`AllItems.aspx?id=%2FDocument%2F...`, `/:x:/r/Document/...`) розпізнаються і виправляються. | P2 |
| RUL-8 | Валідація набору правил на старті: дублікати, конфлікти, цикли (A→B, B→A), неідемпотентність (результат правила знову збігається з якимось правилом). | MVP |
| RUL-9 | Команда `rules test <url>` показує, яке правило спрацює і який буде результат. | MVP |
| RUL-10 | Правила з регулярними виразами. | P3 |

## 9. Повторна обробка невдалих файлів

Мета: наприкінці прогону кожен файл має фінальний статус, а все, що не вдалося обробити, можна повторити вибірково, без повного проходу бібліотеки.

### 9.1. Класи помилок

| Клас | Приклади | Автоповтор | Що далі |
|---|---|---|---|
| `transient` | Обрив мережі, 5xx, 429 після вичерпання повторів, таймаут | Так | Рівень 2 |
| `conflict` | 412: файл змінили під час обробки | Так, із завантаженням нової версії | Рівень 2 |
| `locked` | 423, check-out, файл відкритий на спільне редагування | Так, відкладено | Рівень 3 |
| `excel` | Таймаут або падіння Excel | Так, 1 раз в іншому процесі Excel | Далі потребує уваги |
| `auth` | 401 після оновлення токена, 403 | Ні | Масові 401 зупиняють прогін (запобіжник); поодинокі 403 потребують уваги |
| `file` | Пошкоджений архів, зашифрований, непідтримуваний формат, завеликий | Ні | Потребує уваги |
| `validation` | Самоперевірка після заміни не пройшла (OOX-14) | Ні | Потребує уваги; файл не записується |
| `internal` | Неочікувана помилка в самому інструменті | Ні | Потребує уваги; у журналі повний stack trace |

Окремо від помилок — статус `residual`: заміни виконано, але у файлі лишилися старі префікси (RES-2). Такі файли переглядаються окремим фільтром і повторюються після доповнення правил.

### 9.2. Рівні повторів

| Рівень | Коли | Як | За замовчуванням |
|---|---|---|---|
| 1. Запит | Невдалий окремий HTTP-запит | Повтор запиту з `Retry-After` і експоненційною паузою (RSL-2, RSL-3) | До 6 спроб |
| 2. Файл у прогоні | Класи `transient`, `conflict`, `excel` | Файл повертається в чергу з паузою. Кожна спроба починається з нового завантаження і свіжого eTag. | Паузи 1, 5, 15 хв; до 3 спроб |
| 3. Відкладені | Клас `locked` | Обробляються хвилями після основної черги, поки не мине ліміт часу | Хвиля кожні 10 хв, ліміт 2 год |
| 4. Повторний прогін | Після завершення прогону, вручну | Команда `retry` або кнопка в GUI; файли вибираються фільтром; бібліотека повторно не перелічується | — |

Усі паузи, кількості спроб і ліміти налаштовуються в конфігу.

| ID | Функція | Пріоритет |

| RTY-1 | Класифікація кожної помилки (9.1) з етапом, HTTP-кодом, повідомленням і `request-id` SPO (для звернення в підтримку Microsoft). | MVP |

| RTY-3 | Автоматичні повтори рівнів 1–3. | MVP |
| RTY-4 | Повторний прогін з вибором файлів: за статусом, класом помилки, бібліотекою, форматом, маскою шляху, списком з CSV або виділенням у GUI. | MVP |

## 10. Графічний інтерфейс і дашборд

Архітектура:
- **Рушій** працює як фоновий процес (хост) на виділеній машині або ВМ і веде всі прогони. Стан — у базі SQLite (розділ 8).
- **GUI** — вебінтерфейс, який віддає той самий хост; відкривається в браузері. Закриття браузера не зупиняє прогін; дашборд можуть дивитися кілька людей одночасно.
- **CLI** працює з тим самим рушієм — для запуску за розкладом і автоматизації.

### 10.1. Дашборд і прогони

| ID | Функція | Пріоритет |
|---|---|---|
| GUI-1 | Дашборд поточного прогону з оновленням у реальному часі (1–2 с): знайдено файлів; оброблено / всього (%) і орієнтовний час завершення; змінено; без змін; замін усього і за типами (Hyperlinks, Link Sources, формули тощо); помилки за класами; відкладені; з залишками; швидкість (файлів/хв, МБ/с); активні обробники; стан throttling. | MVP |

### 11.1. Керування навантаженням на SPO (throttling)

Ліміти SPO за документацією Microsoft ([Avoid getting throttled or blocked in SharePoint Online](https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online), станом на 10.2026) рахуються в **ресурсних одиницях (RU)**: читання елемента і завантаження файлу — 1 RU, delta з токеном — 1 RU, перелік, створення, оновлення, вивантаження — 2 RU, операції з правами — 5 RU.

| Рівень | Ліміт (залежить від кількості ліцензій тенанта) |
|---|---|
| Застосунок у тенанті | 1 250 – 6 250 RU/хв; 1,2 – 6 млн RU/добу; 400 ГБ/год вивантаження і завантаження |
| Тенант загалом (усі застосунки і користувачі разом) | 18 750 – 93 750 RU / 5 хв |

> **Важливо про кілька застосунків.** Microsoft прямо не рекомендує створювати кілька App ID для однієї задачі, щоб обійти ліміт застосунку: усі застосунки ділять один тенантний бюджет, і такий підхід виснажує його та призводить до throttling інших застосунків і користувачів, а при тривалому перевищенні — до блокування застосунку. Три застосунки на повному ліміті вже дорівнюють усьому тенантному бюджету на будь-якому діапазоні ліцензій.
>
> Тому кожен застосунок працює в межах свого ліміту (THR-1…THR-8), а пул застосунків (THR-9…THR-11) входить у MVP із жорсткою стелею тенантного бюджету і вмикається в профілі явно.

**Робота в межах одного застосунку:**

| ID | Функція | Пріоритет |
|---|---|---|
| THR-1 | Бюджет RU на застосунок: облік вартості кожного запиту за таблицею Microsoft; token bucket з хвилинним і добовим лімітом; робота нижче порогу (за замовчуванням 80% ліміту), щоб 429 не виникали взагалі. | MVP |
| THR-2 | Ліміти обчислюються з діапазону ліцензій тенанта (вибір у GUI), з можливістю ручного коригування. | MVP |
| THR-3 | Реакція на 429/503 для всього застосунку: `Retry-After` зупиняє всі потоки цього застосунку, а не один запит; після паузи — плавне нарощування паралельності. | MVP |
| THR-4 | Мінімум запитів на файл: метадані з delta (без окремого GET), завантаження за `@microsoft.graph.downloadUrl`, вивантаження одним запитом для невеликих файлів, без `$expand=permissions`, лише Graph (REST — тільки для UPL-5). Ціль: ~2 RU на файл без змін, ~4 RU на змінений. | MVP |
| THR-5 | Вікна роботи за розкладом: окремі бюджети для робочого і неробочого часу (часовий пояс тенанта), автоматична пауза і продовження. | MVP |
| THR-6 | Добовий бюджет: облік RU за ковзні 24 год; при наближенні до ліміту — автоматична пауза до відновлення. | MVP |
| THR-7 | Виявлення блокування: тривалі 503 на всі запити → зупинка прогону і сповіщення, без подальших спроб (вони лише подовжують блокування). | MVP |
| THR-8 | На дашборді: використання бюджету RU (за хвилину і за добу) по кожному застосунку і сумарно, кількість 429/503, поточні паузи, ефективна паралельність. | MVP |

**Пул застосунків:**

| ID | Функція | Пріоритет |
|---|---|---|
| THR-9 | Кілька підключень (App ID + сертифікат) в одному прогоні. Кожен застосунок має власні токени, бюджет RU і стан throttling. Планувальник віддає файл застосунку з вільним бюджетом; повний цикл файлу (завантаження → вивантаження) виконує один застосунок. Throttling одного застосунку не зупиняє інші. | MVP |

| THR-11 | Пул вмикається лише явно, з попередженням у GUI про рекомендацію Microsoft. Перед стартом перевіряється, що кожен застосунок пулу має доступ до всіх цілей профілю. | MVP |
